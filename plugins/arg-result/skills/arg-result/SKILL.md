# arg-result

讓論點互相攻擊，留下攻不倒的。

成品只有一樣：**每一輪都沒被推翻的論點**，以及它們剝到最底層的樣子。辯論過程是手段，不是成品。

## 這是什麼、不是什麼

- **不判勝負。** 哪一方贏不重要，重要的是哪些話經得起攻擊。兩方各自留下的論點合起來，才是對命題的回答。
- **不是優缺點清單。** 從沒被攻擊過的論點不算「站得住」，報告裡另外列。
- **不是主持人的意見。** 主持人（你）不加入辯論、不替任一方補論點。最後的總結只能重述存活的論點。
- **慢，而且耗用量。** 預設最多 5 回合：辯手發言約 10 次、裁判約 11 次。實測 3 回合約 75 分鐘（辯手每次 2–7 分鐘、裁判每次 2–5 分鐘），5 回合約 2 小時。開始前先跟使用者說。

## 角色

| 角色 | 由誰擔任 | 看得到什麼 |
|---|---|---|
| 主持人 | 你（執行這個 skill 的 session） | 全部。負責傳話、存記錄、在需要時停下來問使用者 |
| 正方 | 一個獨立 subagent，整場用同一個 | 命題、定義、對方說出口的發言、裁判的公開裁定、帳本 |
| 反方 | 一個獨立 subagent，整場用同一個 | 同上 |
| 裁判 | 一個獨立 subagent，整場用同一個 | 全部公開發言與帳本。不站任何一方 |

**為什麼要分成三個 AI。** 同一個腦袋同時演兩方，會不自覺替一方放水，也會把自己的反駁寫得剛好打得到。分開以後，一方只看得到另一方說出口的話，才像兩個真的人。裁判獨立，是因為讓辯手自己判會有兩種失敗：一被質疑就客氣讓步，或者死不認輸。

**主持人只傳原文。** 不摘要、不加評語、不暗示該攻哪裡。主持人一旦帶風向，分開三個 AI 就白做了。

## 第 0 步：釐清命題

1. **解析輸入。** 命題 M 是使用者給的整段話。結尾若有 `n=K`、`K 輪` 或 `--rounds K`，就是指定的回合數。
2. **改寫成可以辯的兩個立場。** M 是開放式問題（「……的意義在哪？」）時，正方主張「有，而且具體在這些地方」，反方主張「沒有，或遠小於一般以為的」。這樣雙方存活的論點合起來，就是對原問題的回答。
3. **定義關鍵名詞與範圍。** 例如誰算「資深工程師」、說的是今天的 AI 還是五年後的 AI。
4. **找出 M 自帶的前提。** 「AI 這麼方便」就是一個。預設把它當成既定前提：可以爭它的程度，但整個否定它就算離題。
5. **有疑問就停下來問。** 某個名詞有兩種以上的合理理解、會讓雙方辯成兩件事；或者 M 自帶的前提本身就是最大爭點；或者 M 其實是查一下就有答案的事實問題——這三種情況，用 AskUserQuestion 問使用者，附上你建議的定義或處理方式。沒有這些情況就直接開始，不要為問而問。
6. **開場告訴使用者**：雙方立場、定義、回合數、大概要多久（3 回合約 75 分鐘，5 回合約 2 小時）。

## 第 1 步：建工作目錄，開三個 agent

先在 session 的 scratchpad 目錄（沒有的話用 `$TMPDIR`）建 `arg-result/<短名>/`，不要放進使用者的專案目錄。裡面放兩個檔：

- `transcript.md`：記錄檔。每位發言者把自己的完整輸出**自己附加**到檔尾。
- `ledger.md`：帳本。只有裁判寫，每次整份覆寫。

這樣做有兩個原因。第一，發言一字不改留在檔案裡，主持人不必重打一次；試跑時主持人把每段發言重打三次（顯示、存檔、轉交），既耗用量又可能抄錯。第二，下一位發言者直接讀檔，拿到的一定是原文。

讀 `references/debater.md` 和 `references/judge.md`，把 `{…}` 佔位符填好（含兩個檔案的絕對路徑），用 Agent 工具開 agent：

1. 先開**正方**，任務是第 1 回合立論。
2. 正方講完，開**裁判**，第一個任務是裁定正方的立論。
3. 裁判裁定完，開**反方**，第一個任務是讀記錄檔裡的正方立論和裁判裁定，再反駁並立論。

記下三個 agent 的 ID。之後每次發言都用 SendMessage 接續**同一個** agent，讓它記得自己查過的資料、說過的話。SendMessage 如果是延遲載入的工具，先用 ToolSearch `select:SendMessage` 載入。

沒有 SendMessage 可用時，每次都重開新 agent，給它完整的公開記錄、帳本和它自己之前的發言。所有狀態本來就寫在記錄和帳本裡，所以結果一樣，只是比較慢。

agent 在背景跑時，等它的完成通知，不要預測它會說什麼。**正反方絕不同時跑**：一方講完、裁判裁定完，另一方才拿到內容。這就是比賽的「一步一步來」。

## 第 2 步：回合

每一回合依序四步：

1. **正方發言**（它自己附加到記錄檔）→ 主持人把精簡版顯示給使用者：每條論點、每次攻擊各一兩句
2. **裁判裁定正方**（它自己附加裁定、覆寫帳本）→ 主持人顯示裁定要點
3. **反方發言** → 同 1
4. **裁判裁定反方**，並視情況提出本回合的底層前提 → 同 2

主持人的訊息只負責叫下一位發言，固定用這個格式：

```
第 {r} 回合{（結辯回合）}。
先讀 {transcript.md 絕對路徑} 的最後兩節（對方剛才的發言、裁判的裁定），以及 {ledger.md 絕對路徑}（目前帳本），再發言。
裁判列在「下一位發言者必須處理」的每一項都要處理。
{結辯回合時，附上下面的結辯規則}
```

給裁判的訊息同理：「請讀 transcript.md 最後一節（{方}第 {r} 回合發言），裁定後附加到記錄檔、覆寫帳本。」agent 讀不到檔案時，退回把原文直接貼進訊息。

每次發言的結構是：答詢 → 答辯 → 反駁 → 新論點 → 質詢 → 承認（細節在 `references/debater.md`）。第 1 回合正方只有立論。

### 結辯回合

最後一回合是結辯，規則和一般回合不同，因為每一次攻擊都要讓對方有機會回應：

- 雙方都**不能提新論點**。
- 被攻擊的論點**可以修正**成更窄的版本；裁判提出的底層前提，也可以由負責防守的一方修正。修正版要通過裁判的三項檢查，狀態記「結辯修正，未再受考驗」。因為之後沒有回合能再攻擊它，所以不算存活，報告另外列。對方在結辯明確承認的，改為「對方承認」，算存活。這條規則是 2026-11-21 試跑時使用者決定的。
- 正方照常可以攻擊、可以質詢；反方會在同一回合回應。
- 反方**不能發新攻擊、不能質詢**，因為正方之後沒有發言機會了。
- 結辯回合的前一回合，告訴裁判「不提新的底層前提」，理由相同：新前提需要一個完整的攻防回合。

### 回合數

- **使用者有指定 n**：照做，第 n 回合是結辯。
- **沒指定**：最多 5 回合，至少 3 回合。從第 3 回合起，如果一整回合沒有任何論點被推翻、修正或撤回，也沒有新論點和新的底層前提，下一回合就是結辯。

### 往下剝的機制

只讓雙方一直丟新論點，結果會很寬但很淺。這個 skill 要的是「最底層的概念」，所以有三個設計把辯論往下推：

1. **修正版可以存活。** 論點被打中後縮小範圍、改成守得住的版本，新版本可以繼續存活，報告會附上它的演變過程。被逼著一次次修正的論點，最後通常就剩下最核心的那一句。
2. **第 3 回合起不能開新戰場。** 新論點必須是往下挖的：揭露某個現有論點（哪一方都可以）底下的前提，或者回應裁判提出的底層前提。
3. **裁判提出底層前提。** 表面的論點吵完後，真正的分歧通常卡在雙方都沒說出口的前提上。裁判在回合結束時把它寫成一句可以攻擊的主張（底1、底2……），下一回合由不受它支持的一方攻擊或承認。

## 第 3 步：結束與報告

1. 在請裁判裁定反方結辯的**同一則訊息**裡，請它接著做「最終整理」（見 `references/judge.md` 最後一節）：把存活的論點排成誰依賴誰，找出最底層，寫一到三句總結。這樣省一次來回。
2. 依 `references/report.md` 寫報告。報告內容只能來自最終帳本、裁判的最終整理和記錄檔，不能有任何新主張。附錄直接接上 `transcript.md` 全文。
3. 存檔：`./arg-result/<命題前 20 字，去掉標點>-<YYYY-MM-DD>.md`。同名檔存在就加 `-2`。如果目前目錄在 git repo 裡，先問使用者要放哪，不要擅自寫進別人的程式碼專案。
4. 在對話裡顯示報告的「剝到最底層剩下的」和「沒被推翻的論點」兩節，再附上檔案路徑。

## 什麼時候停下來問使用者

使用者要的是「有疑問才停」。以下情況停下來用 AskUserQuestion 問，其餘時候一路跑完：

- 第 0 步列出的那三種情況。
- 同一個「未決」爭點連續兩回合都沒進展，雙方在原地繞圈。這時問使用者要親自裁定，還是保留成未決、讓辯論往別處走。這類爭點通常是價值判斷（例如「負責比效率重要嗎」），使用者自己的價值觀本來就是合法的裁判。
- 雙方離題，在辯另一個命題。
- 辯手連續兩次不照格式，或拒絕扮演自己的立場。
- 工具失敗（agent 起不來、碰到用量上限）。說明卡在哪一步；之後可以用 SendMessage 從同一處接續，不必重來。
- 網路中斷（例如 `ENOTFOUND`）不用先問：確認連線恢復後，自動用 SendMessage 叫同一個 agent「重做上一個任務」，重試一次。它記得前面的內容，辯論不必重來。再失敗才停下來說明。

裁判在「需要主持人處理」寫的事，先看是不是使用者已經決定過的同類情況。是的話比照辦理，在對話裡說一聲；只有真正的新規則漏洞才問使用者。

## 品質檢查（交報告前）

- 每一條存活論點都受過至少一次有效攻擊，或者被對方明確承認。兩者都沒有的，放「沒被攻擊過」那一節。
- 每一條修正版都附上演變：原本怎麼說、被哪個攻擊逼成現在這樣。
- 「結辯修正，未再受考驗」的論點沒有混進存活清單。
- 對方承認時附的理由只涵蓋論點一部分的，報告裡註明涵蓋到哪裡。
- 總結的每一句，都能對應到帳本裡某個存活論點的編號。
- 報告裡的來源連結，都是辯手真的引用、裁判沒判造假的。
